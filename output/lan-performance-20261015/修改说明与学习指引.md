## 1. 显卡取帧：从屏幕截图换成 DXGI 桌面复制

入口在 [WindowsAPIScreenCapture.CaptureScreen](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach.Windows/WindowsAPIScreenCapture.cs:61>)；实际显卡取帧在 [DesktopDuplicationCapture.CaptureFrame](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach.Windows/DesktopDuplicationCapture.cs:60>)。

`WindowsAPIScreenCapture` 是本项目的类名，原来这个方法内部使用的是 GDI 的 BitBlt。性能要看方法内部做了什么，不能仅根据类名判断。

这里采用 DXGI Desktop Duplication。AcquireNextFrame 返回桌面图像的 Direct3D 资源；QueryInterface 得到 ID3D11Texture2D。现有 JPEG 编码运行在 CPU 上，因此仍需要 CopyResource 将图像复制到 CPU 可读的 staging 纹理，然后 Map 得到可读取的 DataPointer。显存资源对象不能直接当作普通的 CPU 指针访问。[微软桌面复制说明](https://learn.microsoft.com/en-us/windows/win32/desktop-dup-api)、[MapDesktopSurface 的 CPU 访问条件](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-mapdesktopsurface)。

关键代码是：

```csharp
context.CopyResource(stagingTexture, texture); // 目标、源
var mapped = context.Map(stagingTexture, 0, MapMode.Read, MapFlags.None);
try
{
    CopyRows(mapped);
}
finally
{
    context.Unmap(stagingTexture, 0);
}
```

CopyRows 必须按 RowPitch 逐行复制。GPU 每行可能附带对齐字节，不能假设整张图片连续占用 width × height × 4 字节。Map 得到的指针只在映射有效期间使用，复制后立即 Unmap；取得的桌面帧在 finally 中 ReleaseFrame。返回的 Bitmap 由捕获器持有并复用，外层在下一次捕获之前完成缩放和编码。

这轮仍然存在显卡到 CPU 的像素拷贝。进一步减少该拷贝需要让缩放、编码继续使用 GPU 纹理，属于后续编码链路的改造。

会话持有一个捕获器实例；D3D 设备、staging 纹理和位图缓冲区被复用。DXGI 出错时释放复制接口，先回退 GDI，5 秒后再尝试恢复。当前复制主屏，旋转显示器使用 GDI 回退。

AcquireNextFrame 超时表示暂时没有新桌面帧，本次返回 null，发送端跳过编码和发送。静止桌面不会为了显示 30fps 而重复发送同一幅图；应在拖动窗口或滚动时观察流畅度。[AcquireNextFrame 的超时与帧获取约定](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe)。

为适配现有 .NET Framework 4.7.2，本轮引入支持 .NET Standard 2.0 的 [Vortice.Direct3D11 1.9.143](https://www.nuget.org/packages/Vortice.Direct3D11/1.9.143)，没有升级项目框架。

## 2. 任务重叠：普通 lock 会等待，TryEnter 会跳过

修改 [ScreenPlugin.SendFrame](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach/Plugins/Screen/ScreenPlugin.cs:77>)。

普通 `lock (sendFrameLock)` 会让多个定时器回调排队等待；轮到它们时，仍会继续处理已经过时的捕获任务。这里用立即返回的 TryEnter：

```csharp
if (!IsEnabled || !Monitor.TryEnter(sendFrameLock)) return;
try
{
    // 截图、JPEG、GZip、打包并提交发送。
}
finally
{
    Monitor.Exit(sendFrameLock);
}
```

第一帧占用锁时，新的触发拿不到锁，直接 return。第一帧结束后，下一次触发才开始新截图。finally 保证截图或编码抛异常时也能释放锁。compressed 已从共享字段改为方法内局部变量。

这把锁覆盖截图、压缩和提交发送。Client.SendBytes 仍然使用异步发送，提交后底层 TCP 数据可能尚未发送完成，所以它不是网络发送队列的容量限制。

## 3. 接收积压：只保留一个最新待处理帧

修改 [EnqueueFrame 和 ProcessingFramesThread](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach/Plugins/Screen/ScreenPlugin.cs:131>)。

用一个字段代替 Queue：

```csharp
private byte[] pendingFrame;
```

到达新帧时，覆盖尚未处理的旧帧：

```csharp
lock (queueLock)
{
    pendingFrame = frame;
    Monitor.Pulse(queueLock);
}
```

消费端在同一把锁中取走当前最新帧并将槽位置空，然后到锁外解压和处理：

```csharp
lock (queueLock)
{
    while (pendingFrame == null && !token.IsCancellationRequested)
        Monitor.Wait(queueLock);
    if (token.IsCancellationRequested) return;
    frame = pendingFrame;
    pendingFrame = null;
}
ProcessFrame(frame, token);
```

例如 A 正在处理时，B、C、D 连续到达：待处理槽先后变成 B、C、D；A 完成后直接取 D。最多是一张正在处理，加一张等待处理。

“先 Dequeue 一张，再 Clear”通常会取到最旧的那张，然后把更新的画面丢掉。若继续用 Queue，应取出最后一张；这个场景直接用单个槽位更清楚。简单缩小 FIFO 容量虽然能减轻延迟，仍然没有明确表达保留最新帧的规则。

此策略适用于当前完整、可独立解码的 JPEG。它不能直接套用到依赖之前图像块的差分更新协议。

## 4. 资源释放：具体方法与所有权

| 方法 | 原来的问题 | 当前处理 |
|---|---|---|
| WindowsAPIScreenCapture.GetScreenScalingFactor | Graphics.GetHdc 后没有显式归还 | using Graphics，finally ReleaseHdc |
| WindowsAPIScreenCapture.CaptureGdiFrame | CreateDC 后没有 DeleteDC，原图及 Graphics 不及时释放 | finally DeleteDC；GetHdc 对应 finally ReleaseHdc；位图和 Graphics 作为实例缓冲区复用并在 Dispose 中释放 |
| WindowsAPIScreenCapture.ZipImage | 每帧查找编码器、创建缩略图，编码参数不及时释放 | 编码器缓存；缩放目标缓冲区复用；EncoderParameters 和 MemoryStream 使用 using |
| BitmapExtendsion.ToBitmap | 返回 Bitmap(stream) 后立即关闭它依赖的 stream | 在流和解码图仍有效时，用 LockBits 复制到独立的 32 位 RGB 位图；原始资源在 using 中释放 |
| MasterForm.QueueScreenImage | 旧图片和异步显示请求可能继续积累 | 仅保留最新待显示 Bitmap；被替换的待显示图片立即 Dispose；最多保留一个尚未执行的 UI 回调 |
| MasterForm.DisplayPendingScreenImage | 每帧 GetThumbnailImage，再覆盖 PictureBox.Image，旧图不 Dispose | UI 线程快速缩放；赋新图后 Dispose 旧图；输入原图用 using 释放 |
| MasterForm.DisposeScreenResources | 关闭时未统一停止及清理 | 停止屏幕插件，释放捕获器、待显示图片及已显示图片；由窗体 Dispose 调用 |
| ScreenPlugin.DisablePlugin / Dispose | 定时器及接收线程没有退出路径 | 停止定时器，取消接收循环并唤醒等待；Dispose 释放定时器 |
| Client.Dispose / SlaveForm | 会话释放未通知屏幕插件，受控端隐藏视图也未释放 | 客户端释放插件；受控窗体释放隐藏 MasterForm |

阅读入口：[ToBitmap](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach.Windows/BitmapExtendsion.cs:36>)、[显示队列与图片所有权](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach.Windows/MasterForm.cs:402>)、[捕获器释放](</C:/Users/o/Desktop/新建文件夹/HJJJJ.DeskReach/HJJJJ.DeskReach.Windows/WindowsAPIScreenCapture.cs:150>)。

GDI 资源成对释放的规则：CreateDC → DeleteDC；Graphics.GetHdc → 同一个 Graphics.ReleaseHdc；Bitmap、Graphics、EncoderParameters → Dispose。可复用资源由会话捕获器负责释放，不能由 ZipImage 把借用的原图 Dispose 掉。

图片在接收端的所有权是：ToBitmap 创建独立位图，QueueScreenImage 接管它；新图替换待显示旧图时释放旧图；UI 取走后负责释放输入图和上次显示的图。关闭后到达的图片也会立即释放。

显示端仍保持原来按窗口宽度等比例生成图片的行为。GetThumbnailImage 已替换为 DrawImage，并实测了插值模式；本机 HighQualityBilinear 比普通 Bilinear 更快。名称中的“高质量”不能直接当作耗时判断，最终应以代表性图片和目标尺寸实测。边缘使用 TileFlipXY，避免平滑缩放时出现暗边。

接收队列和 UI 请求队列都需要限制：只改接收队列，却对每一帧调用一次 BeginInvoke，可能把积压转移到 UI 线程。这轮两处都使用最新帧合并。
