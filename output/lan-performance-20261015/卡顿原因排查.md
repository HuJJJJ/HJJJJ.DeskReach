# 局域网卡顿原因排查

日期：2026-10-15。范围：当前 HJJJJ.DeskReach.Windows 主程序、核心屏幕插件和当前 Debug 成品。

此文件保留第一轮修改前的定位基线。后续源码修改、验证结果和学习说明见同目录《修改说明与学习指引.md》。

## 结论

已确认本机截图、缩放和帧调度存在足以拖低帧率的瓶颈。即使不经过网络，当前处理链路也无法据此保证稳定 30fps。间歇性停顿与截图回调重入、旧帧排队及集中丢弃相吻合。实际两端网络吞吐和端到端延迟尚未测量，各因素的实际占比仍需在远程会话中确认。

## 测量方法与结果

使用现有 Debug 成品中的 WindowsAPIScreenCapture.CaptureScreen 方法进行 100 帧测量；JPEG 质量 50。桌面 2560×1440，编码图片 1280×720；显示缩放目标宽度取窗体设计器默认值 1478。接收处理复现现有 GZip 解压、JPEG 解码及 GetThumbnailImage 缩放。各步骤在本机分别计时，未包含网络、协议封装及实际窗口绘制，因此不是实际远程会话帧率；两端耗时不可直接相加后取倒数当作吞吐帧率。

| 步骤 | 平均耗时 | P95 |
|---|---:|---:|
| 截图、缩小并 JPEG 编码 | 60.59 ms | 70.80 ms |
| JPEG 外层 GZip 压缩 | 2.54 ms | 4.12 ms |
| GZip 解压 | 1.16 ms | 4.49 ms |
| JPEG 解码 | 2.69 ms | 3.52 ms |
| 接收端重新生成缩放图片 | 44.55 ms | 50.41 ms |

30fps 的持续处理预算是每帧 33.33ms。截图任务和接收端缩放分别在全部 100 个样本中超出此预算。单个截图执行流加 GZip 的测量吞吐约 15.8fps；接收端顺序解压、解码、缩放约 20.7fps，尚未包含窗口绘制。窗口大小、桌面内容、硬件及系统负载会影响这些数字。

## 按优先级排列的问题

### 1. 每帧两次生成缩略图，截图和显示均超预算

发送端先复制完整桌面，再用 GetThumbnailImage 缩小到一半分辨率，随后编码为 JPEG。接收端每帧解码后，又调用 GetThumbnailImage 生成适合窗口尺寸的新图片。该缩放操作随显示窗口尺寸扩大而变慢：另一次目标宽度 2560 的 100 帧测量中，接收端缩放平均 139.01ms；该值仅是大窗口场景的独立样本。

位置：HJJJJ.DeskReach.Windows/WindowsAPIScreenCapture.cs:64、91、121；HJJJJ.DeskReach.Windows/MasterForm.cs:396。

### 2. 25ms 定时器允许截图回调重入，发送端缺少负载控制

核心屏幕插件定时器设置为 1000 / 40，即名义 40fps；SendFrame 没有防重入，也没有在任务完成后再安排下一帧。以相同 25ms 定时策略调用现有截图方法，在 2 秒测试中完成 63 次回调，最大同时执行 3 次截图。实际发送还会进行 GZip 和打包；共享 compressed 字段也没有并发隔离。

ACK 相关等待已被注释；Client.SendBytes 将数据直接交给 SendAsync，发送任务未被等待，也没有依据传输或接收处理速度限流。网络库存在发送任务队列；实际是否积压以及积压程度尚未测量。

位置：HJJJJ.DeskReach/Plugins/Screen/ScreenPlugin.cs:34、74、85；HJJJJ.DeskReach/Client.cs:150。

### 3. 接收端播放旧帧，积压后突然清空

接收端按 FIFO 逐帧解压和显示，frameQueue.Count > 10 才清空队列。生产快于消费时，会先显示落后的画面，再因清空而跳到较新的画面。十余帧按约 20fps 消费，可能额外引入约半秒级排队延迟，具体取决于实际生产和消费速率。该机制直接符合“时卡时不卡、画面突然跳”的表现。

位置：HJJJJ.DeskReach/Plugins/Screen/ScreenPlugin.cs:102、118。

### 4. 图形资源释放不完整，持续运行会加重压力

截图函数每次创建显示设备上下文，但没有 DeleteDC；原始位图和多个 Graphics 也没有及时 Dispose。GetScreenScalingFactor 取得 HDC 后没有显式释放。接收端生成新显示图片后，未显式释放 tempFrame 和被替换的旧 pictureBox.Image。

现有截图方法在 100 帧测试中，GDI 对象从 8 增至 111；强制垃圾回收后仍为 108，即残留增长 100。该测试确认截图路径存在持续图形句柄泄漏。内存由约 62.8MB 升至 95.0MB，强制回收后约 63.4MB；这部分内存增长主要可回收，不能全部当作永久内存泄漏。

位置：HJJJJ.DeskReach.Windows/WindowsAPIScreenCapture.cs:56、64；HJJJJ.DeskReach.Windows/MasterForm.cs:396。

### 5. 次要开销与质量设置问题

- 当前主程序发送完整 JPEG，每帧外面再包 GZip。本次样本平均只节省约 7.43% 体积，压缩平均花费 2.54ms。JPEG 平均 93,736 字节，GZip 后 86,774 字节；按名义 40fps 约需 27.8Mbps 的图像净负载，但这不是网络吞吐测试，复杂画面大小会变化。
- 菜单初始显示 Speed，但设置 SelectedIndex 时尚未绑定 SelectedIndexChanged，因此初始不会发送质量 0；发送端仍保留默认质量 50。切换到其他档位再切回 Speed 才会触发对应参数。
- 接收线程直接更新 WinForms 控件，主窗体关闭了跨线程检查；这增加了显示并发风险，尚未单独量化。
- 屏幕定时器和接收线程缺少停止及退出路径，Client.Dispose 只释放网络对象；关闭会话后残留工作可能继续消耗资源，尚未在反复重连场景量化。

## 实际启用的代码路径

主程序 MasterForm 和 SlaveForm 引用 HJJJJ.DeskReach.Plugins.Screen，使用核心项目中的完整 JPEG 传输。HJJJJ.DeskReach.Plugins.Screen.Windows 中另一套分块像素更新实现没有被当前主程序注册，不能把那套实现当成本次运行链路；其代码被 Demo 引用。

## 建议的修复顺序

1. 调整截图和显示的缩放方式，减少每帧创建图像与资源，补齐图形资源释放。
2. 采用不会重入的截图循环，并限制在途帧数；接收端对完整 JPEG 保留最新待处理帧，避免累积旧帧。
3. 将画面更新集中到 UI 线程，合并过时显示请求并释放旧图像；补齐会话关闭逻辑。
4. 对比评估去掉 JPEG 外层 GZip，修正初始质量参数，再测两端吞吐、显示帧率及画面延迟。
5. 在基础瓶颈消除后，再评估变化区域更新或视频编码的收益。
